Native Windows cache AdvanceOnly compatibility investigation, 2026-10-04

EMULATOR RESEARCH ONLY. System-volume stability remains unproven.
Native Cc sends FileEndOfFileInformation with AdvanceOnly set. A read-only
entry breakpoint captured this for the \$$Fat$$ stream at size1253376.
The old VFAT implementation ignores AdvanceOnly and enters ordinary resizing,
including volume-directory locking, while the cache manager owns the file
resource. The180-file stress run stalled, and a full-boot run faulted during
cache work; these symptoms are not yet proven consequences of that mismatch.

0050 acknowledges AdvanceOnly without resizing or taking the directory lock.
VFAT already mirrors the logical size into its buffered directory entry in
normal writes/resizes and flushes dirty metadata in cleanup/flush paths.
The FAT and directory metadata streams are not regular files to resize.
The source includes0048 section-growth and0049 FATX32 representation fixes.
125imports resolve to the native NT5 images. Runtime testing is in progress.

Primary reference for the distinction between AdvanceOnly and real truncation:
https://github.com/microsoft/Windows-driver-samples/blob/main/filesys/fastfat/fileinfo.c
The checked-in ReactOS fastfat counterpart also handles AdvanceOnly separately;
VFAT (the FATX-capable implementation) did not inspect this flag.
No hardware upload or physical-disk modification has occurred.
