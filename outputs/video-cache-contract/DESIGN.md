# Read-only cache contract diagnostic

Use a fresh child of the unchanged qualified0105 emulator fixture. Reuse pinned
probe107 and the existing0094 read-only mapping observer miniport. The latter
keeps0093 mapping requests and adds bounded PAT/MTRR/CPUID records; its historical
physical popup failure remains a failure. This is not a candidate speed driver.

Observe the installed kernel's MmMapIoSpace and MmMapVideoDisplay calls for
exact4MiB framebuffer physical ranges03C00000/F3C00000. Pair entries/returns by
thread and stack, including nested APIs. Pin code before interpreting it. Bound
all entry stops and elapsed time, remove all breakpoints, resume in finally.
At the first direct-RAM map entry take one64MiB snapshot of the early current
root to determine whether loader aliases still exist at that handoff. At first
probe marker take a coherent64MiB snapshot for all active CR3 aliases,
bootvid ownership and current PTE flags. No code/register/PTE/MSR cache edits.

Read the0094 mapping-time MSRs from its owned seeded trace after normal restart;
do not describe them as simultaneous desktop-snapshot MSRs. Correlate mapping
arguments, result pointer, observed mapping record and full snapshot ranges.
All expected phases and cold/event/workload gates must pass. No repeated launch
or collection, no physical access, no inherited event waiver, no timing claim.

The tested question is which actual mapping API/cache arguments create the two
live aliases and what cache configuration accompanies desktop mapping. This is
a prerequisite to POLICY.md, not a write-combining implementation or benchmark.
