# Legacy non-HD feasibility

The 0.1.0 physical installation used dashboard F as Windows C, XWNFBoot on E, and a 4 MiB framebuffer reservation. Its archived snapshot is file-level and was not restore-tested. `outputs/release-0.1.0/release.json` pins the exact historical F boot and drivers. The configured 640x480 registry defaults in `outputs/video-physical-review159/REPORT.md` are not measured runtime geometry. The v0.1.0 trace miniport requires a freshly initialized trace on every boot; an old populated trace deliberately stops boot. The later 0093 miniport, SHA-256 `3e74a5c35b68d7fa0e047b4ba9cec25e7ec0ea5a94e796fc07508f667fcc85cf`, retained a valid trace and passed two physical repeat boots, but the observed Windows geometry was 1024x576x32, not 640x480 (`outputs/video-trace-reuse-settled/README.md`). Its trace file remains required.

The standard E HD chain in `outputs/stock-boot334/build001.json` has both E-root boot and HD reservation enabled. A 640 or 1024 package cannot be established merely by changing an INI or substituting its launcher: a mode-specific fixed timing/handoff and matched non-HD E loader, memory map, HAL, boot video, display driver, valid trace and installed configuration must be reconstructed and qualified together. No such E fixed profile was found in this bounded review. The F snapshot is historical evidence, not a tested E bundle. No console access or new build was performed for these modes.
